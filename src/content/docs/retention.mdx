## The three tiers

Every signal in Meridian lives in exactly one of three tiers at any
moment. Tiers are mostly invisible at query time — the console fans out
to all three — but they decide how fast a query returns and how much you
pay for it.

<Cards columns={3}>
  <Card title="Hot" subtitle="0–30 days">
    Uncompressed columnar files in NVMe. Sub-second queries, full text indexing,
    every attribute searchable.
  </Card>
  <Card title="Warm" subtitle="30 days – 13 months">
    ZSTD-compressed parquet on object storage. 2–8s queries. Indexed on a
    curated set of attributes you nominate per workspace.
  </Card>
  <Card title="Cold" subtitle="13 months – 7 years">
    Glacier-class deep archive. Restore window is 4h. Used for compliance, not
    for debugging.
  </Card>
</Cards>

## Default policy

Every new workspace starts with the following retention policy. You can
change it any time, including for already-stored data.

## Changing the policy

Retention is a workspace-level setting. To change it, edit
`workspace.toml` and push:

```toml title="workspace.toml"
[retention.logs]
hot  = "30d"
warm = "13mo"
cold = "off"

[retention.traces]
hot  = "14d"
warm = "13mo"
cold = "off"
```

```bash
meridian workspace apply
```

The control plane re-indexes in the background. Hot → warm migrations
finish in minutes; warm → cold takes overnight.

## What a query against each tier feels like

<Tabs>

<Tab title="Hot">
Sub-second on most queries. Free-text search, regex, full attribute
faceting all work without configuration.

```sql
SELECT trace_id, duration_ms
FROM traces
WHERE service = 'checkout'
  AND duration_ms > 2000
  AND ts > now() - interval '6 hours'
```

</Tab>

<Tab title="Warm">
Bounded by parquet scan time. The query planner uses your nominated
indexes; everything else is a full scan over the matched partitions.

```sql
SELECT count(*)
FROM logs
WHERE service = 'api'
  AND level   = 'error'
  AND ts BETWEEN '2026-01-01' AND '2026-01-31'
```

</Tab>

<Tab title="Cold">
Cold queries are not interactive. They submit a restore job, you get a
notification when the slice is back in warm, then you query as normal.

```bash
meridian restore \
  --signal traces \
  --service checkout \
  --from 2025-04-01 --to 2025-04-07
# → restore.4f3a2e1 queued · ETA 03h17m
```

</Tab>

</Tabs>

<Callout variant="warn">
  Cold restores count toward your monthly egress allowance. Restoring a full
  month of trace data for a busy service can run into the tens of thousands of
  dollars on the underlying object store.
</Callout>

## What never moves

A handful of records stay in hot for the entire workspace lifetime,
regardless of policy:

- **Budget events** — every burn, every reset, kept forever.
- **Pipeline changes** — every apply, with the diff and the actor.
- **Workspace audit log** — who logged in, who changed what.

This is non-negotiable; it's the part of Meridian that has to outlast any
single incident.
