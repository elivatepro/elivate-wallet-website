## What a pipeline is

A pipeline is an ordered list of transforms applied to OTLP records as
they arrive at the ingest edge. Pipelines run _before_ storage, which
means anything you drop or rewrite at this layer never touches your bill,
your retention floor, or your downstream queries.

<Steps>

<Step title="Define the pipeline">
Pipelines live in `pipelines/<name>.toml` inside your workspace
configuration repo. Each file is a single pipeline; ordering inside the
file is the execution order at the edge.

```toml title="pipelines/api-prod.toml"
match  = "service.name = 'api' AND env = 'prod'"
sample = { rate = 0.1, keep_errors = true }
redact = ["http.request.body", "user.email"]
```

</Step>

<Step title="Apply it">
Push the file via the CLI. The control plane validates the syntax,
estimates the budget impact, and rolls the pipeline out to the edge in
under a minute.

```bash
meridian pipeline apply pipelines/api-prod.toml
```

</Step>

<Step title="Verify">
The CLI returns the new pipeline ID and the estimated change in record
volume. Spot-check the math against the live ingest dashboard before you
forget about it.

```bash
meridian pipeline status api-prod
# api-prod  ·  active  ·  -88.2% volume  ·  edge.us-east, edge.eu-west
```

</Step>

</Steps>

## Transform reference

<Tabs>

<Tab title="Sampling">
Probabilistic, with an `keep_errors` escape hatch so failed traces aren't
diluted by the rate.

```toml
sample = { rate = 0.05, keep_errors = true }
```

| Field         | Type    | Default | Notes                                        |
| ------------- | ------- | ------- | -------------------------------------------- |
| `rate`        | float   | 1.0     | 0.0–1.0; applied per-trace, not per-span.    |
| `keep_errors` | boolean | true    | Always keep traces containing an error span. |
| `seed`        | string  | host    | Hash key for reproducible decisions.         |

</Tab>

<Tab title="Redaction">
Deletes the listed attributes before storage. Operates on attribute
*paths*, so dotted keys work as you'd expect.

```toml
redact = ["http.request.body", "user.email", "db.statement"]
```

Use this for PII you should not have, not as a substitute for not
collecting it in the first place.

</Tab>

<Tab title="Derived metrics">
Promote a high-cardinality span attribute into a low-cardinality metric
without a re-deploy of your service.

```toml
[[derive]]
from   = "trace"
where  = "name LIKE 'POST /checkout%'"
metric = "checkout.duration"
value  = "duration_ms"
labels = ["status_code", "region"]
```

</Tab>

</Tabs>

## Pipeline file layout

A typical workspace keeps one pipeline per service-environment pair, with
shared rules pulled into a `_lib/` folder.

## When pipelines aren't enough

<Accordion>
  <AccordionItem title="You need to enrich with external data">
    Pipelines run at the edge with no network egress. If you need to look up a
    customer tier or join against a feature flag, do it at the application layer
    and emit the result as a span attribute — then a pipeline rule can route on
    it.
  </AccordionItem>
  <AccordionItem title="You need conditional sampling per user">
    The `sample` transform takes a `seed` parameter. Set it to a user-stable
    attribute and the same user's traces will be kept or dropped consistently
    across the whole window.
  </AccordionItem>
  <AccordionItem title="You need to drop spans, not whole traces">
    Use the `prune` transform with a span-level `where` clause. Beware: pruning
    spans inside a kept trace breaks the parent-child chain and will show as
    gaps in the waterfall view.
  </AccordionItem>
</Accordion>

> **Cost tip.** Most teams over-collect debug logs by 50–100×. A single
> `match = "level = 'debug'" → sample { rate = 0.01 }` rule typically
> pays for the workspace inside the first week.
